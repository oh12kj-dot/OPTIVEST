# OptiVest initial design — DRAFT v0.1

Author: Astra, 2026-09-07. Authority: selected `OPTIVEST_AI_POLICY_V10.md`, SHA-256 `ACF013CE46F450423D83DEEBA1C207B22C669670C2B9BDC83A8A665F5AD38E67`. This document proposes implementation boundaries and acceptance evidence; it does not replace the Policy or approve investor-specific settings.

## Highest priority and scope
Phase 0 makes the governing version and unavailable approvals/evidence visible and reproducible. Its candidate implementation is a standard-library, offline startup verifier, with no trading/forecast/optimization output. A complete model cannot be designed or frozen from missing mandate/data/calibration inputs. No database, framework or provider package is selected prematurely.

### Phase 0 proposed contract for pre-implementation review
`scripts/verify_startup.py` reads an explicit workspace root, hashes actual Policy bytes and verifies START_HERE's filename/hash, verifies required §17 files exist and are nonempty except an intentionally empty RESEARCH_TRIALS.jsonl, checks actual branch/HEAD against recorded values (UNBORN allowed only for a verified repository without commits), validates any existing research JSONL records for the §17 required keys without modifying them, and checks the production evidence register covers exactly selected Policy §18 items 1–25 without claiming readiness.

Output: machine-readable JSON with `startup_integrity` PASS/FAIL, findings with reasons, actual Policy hash, branch/HEAD, and `production_readiness` always `NOT PRODUCTION READY` for Phase 0. A successful startup means only internally consistent governance files. It never authorizes investment output. Unknown/missing/inconsistent files, malformed records or unavailable Git must fail startup, with no automatic rewriting by the verifier. Readonly, deterministic apart from observed Git state, no network, no dependency install. Expected process exit 0 for verified startup integrity, nonzero otherwise. The evidence register itself is a manual status document, not a runtime authorization certificate.

Minimal tests use isolated temporary repositories: valid unborn startup; policy-byte mutation; missing/blank required record; malformed JSONL; missing provenance key; recorded branch/HEAD mismatch; invalid/missing/duplicate evidence item; missing Git repository; and ensure startup PASS still returns NOT PRODUCTION READY. No market simulation is treated as model evidence. Null trial provenance is permitted only for explicitly non-applicable fields with a nonempty reason; unavailable/unknown provenance fails and cannot be recorded as non-applicable. No trial is generated for file bootstrap.

Implementation details are frozen for the narrow Phase-0 Git identity amendment by ADR-0019 / D0011: revisions 2–4 define `STATE_SHA256`, hidden-index flags, portable ASCII paths and closed Git failures. The original Phase-0 rules below remain the retained baseline outside that amendment; independent post-validation is still required before any initial commit or push.
- Fixed §17 required file names: AGENTS.md, .ai/START_HERE.md, HANDOFF.md, DECISIONS.md, FILE_MAP.md, TEST_STATUS.md, RESEARCH_TRIALS.jsonl and TODO.md (the seven last names are all under .ai). PRODUCTION_GATE.json is an additional Phase 0 register. Blank documents fail; a zero-record research ledger is valid only as no experiments yet, never evidence of validation.
- START_HERE machine fields are the existing unique `Policy filename`, `Policy SHA-256`, `Branch`, `Commit / HEAD` labels. Their grammar is an entire line consisting of `- LABEL: ` followed by one backtick-delimited nonempty value, optionally followed by a space and parenthetical human note. No alternate free-text value is accepted. Duplicate/missing/conflicting labels fail. SHA-256 is 64 hexadecimal characters, case-insensitive for comparison. Phase 0 accepts branch `main`; other branches/detached HEAD require a later scoped contract update. Recorded HEAD is `UNBORN` or a 40-character lowercase Git SHA-1 commit ID and must match the observed repository exactly. Confirm selected exact V10 filename/hash as well as recorded-vs-current equality. Future Policy versions require a review/change to the verifier trust anchor, not just rewriting START_HERE.
- Git failure is not UNBORN. First verify repository/worktree identity and exact resolved Git-root equality, then symbolic branch and commit. UNBORN is valid only when main has no branch ref and no HEAD commit. Reject unreadable/corrupt Git state or an unexpected Git object format. Report actual working-tree dirty status without modifying it. No parent repository may be mistaken for a newly initialized workspace.
- Gate JSON requires unique integer IDs 1–25 (booleans are not integers), exact Policy requirement text, matching top-level `policy_filename` and `policy_sha256`, top-level `scope` exactly `Manual evidence register; not runtime authorization` and `production_readiness` exactly `NOT PRODUCTION READY`. All evidence fields are lists; recognized evidence statuses are PASS / FAIL / NOT VERIFIED / NOT APPROVED / NOT APPLICABLE. NOT APPLICABLE requires an explicit nonempty `rationale` and stays non-PASS for this checker. PASS requires nonempty evidence references but remains an unverified assertion, not a certification. Even a fully populated manual register does not unlock production. Missing/null status is not PASS; no truthy/string coercion. All JSON parsing (gate and ledger) rejects duplicate object keys.
- Trial keys map §17 prose to: trial_id, hypothesis, dataset_snapshot, dataset_hash, commit, feature_parameter_set, risk_budget, oos_period, model_name, model_version, prompt_hash, policy_hash, random_seed, optimizer_version, result, disposition. `disposition` is accepted/rejected. Non-applicable values require a separate `not_applicable_reasons` mapping by key; missing required keys still fail. `trial_id`, `hypothesis`, `policy_hash`, `result`, `disposition` cannot be null. Existing historical trials can have a different valid policy hash; preserve their original provenance and never rewrite them to current Policy. This check is structural, not evidence verification or proof of append-only storage.
- Run command: `python scripts/verify_startup.py --root .`; tests: `python -m unittest discover -s tests -v`. No package installation required. Error messages must identify a reason, not dump sensitive document contents.
- Apply regular-file and resolved-inside-root checks to every inspected governance file, the Policy, and gate register, not only to the Policy path. Test directory/external-link substitution where supported. A before/after byte snapshot of the workspace, including Git files, must prove verification is read-only; configure Git reads so optional index refresh cannot mutate the repository. Check malformed metadata, duplicate JSON keys, boolean IDs, top-level readiness contradiction, and unknown trial provenance with explicit negative tests.
- Gate root permits exactly policy_filename, policy_sha256, scope, production_readiness, items; item permits exactly id, requirement, status, evidence, optional rationale. Trial permits its required keys and optional not_applicable_reasons. Unknown keys fail to expose typos. N/A reasons may name only present, null, nullable required keys; nonempty ledger blank lines fail. Result/hypothesis/IDs cannot be empty. Validate SHA-256 provenance syntax, and require nonempty typed values for other non-null provenance; this does not attest their truth.
- Expected gate requirements come only from numbered items under §18 in the full-read, independently hash-pinned authoritative Policy (never from the register itself); require the exact unique IDs 1–25 in that source too. This avoids duplicating all 25 Policy texts in source code without weakening the independent trust anchor. Read-only report includes explicit capability limits: investment/model, OOS, shadow and approval provenance are not validated; append-only history is NOT VERIFIED. Detect case-insensitive collisions on inspected canonical paths where the filesystem permits them. stdout is one JSON object; findings have stable codes and deterministic ordering; nonzero on failure without printing source contents.
- START_HERE also requires exactly one nonempty current label each: Updated, Current task, Role (including model/effort disclosure), Delegation, Policy version, Decision version, Risk Budget, Mandate, Validation, Production, Next file. These metadata lines use `- LABEL: nonempty text`; only the four strict machine fields above have the backtick/parenthetical grammar. Phase 0 Risk Budget must retain the exact initial backtick token `PROVISIONAL / RISK BUDGET NOT APPROVED` (optional explanatory text follows), and Production the exact backtick token `NOT PRODUCTION READY`. The checker verifies metadata presence/denial state only, not truth of role/model, mandate or decision/review provenance. A missing required metadata field or forged risk/production approval is a negative test. HANDOFF/DECISIONS prose semantics beyond file presence remain explicitly outside this small structural checker and require human review under §17.

Rationale: bare prose cannot cheaply detect hash/HEAD drift; a small offline verifier can. Alternatives: prose only misses machine-detectable mismatches; a full governance platform is premature. Phase 0 does not implement §18 production authorization or portfolio constraints and must not be advertised as doing so.

## Mandate and research risk boundary
Request the §2 required mandate fields from the user. Unanswered values remain NOT VERIFIED. A 7-year BALANCED_RESEARCH_V1 is a Policy-provided research reference, not the user's approved horizon. No ticker, benchmark, base currency or passive implementation is inferred. `docs/RESEARCH_RISK_BUDGET.md` records only §8's provisional defaults and unknowns; an editable UI is a later deliverable, not complete at bootstrap.

## Candidate architecture and data flow — not frozen
One modular application is the initial proposal, with boundaries below; split services only if measured requirements justify it.

1. Evidence ingestion → provider registry + immutable/raw snapshot references + stable security/issuer identities and corporate-action lineage (§5). Preserve observation period, available_at, retrieved_at, source, quality/missingness, and verified latency. Store universe membership/delistings as time-varying records.
2. PIT materialization → decision snapshot with tradable_at, decision timestamp and lineage; reject temporal violations and unresolved material source coverage. Snapshot reconstruction must not replace original vintages with restatements.
3. Forecast → economic return bridge and hierarchical statistical/economic prior (§7), joint path dependencies, company-alpha shrinkage, multi-horizon distributions. Attach an uncertainty ledger with source, transformation, version, role and overlap evidence. No LLM narrative directly reaches a weight.
4. Risk/wealth → one base-currency accounting transition incorporating applicable fees/slippage/tax once; path drawdown/recovery/default events from joint paths, not terminal MOIC. U_risk constraints and separately approved S_stress define feasibility (§8/9/13). Strict log ruin treatment and solver tolerances need explicit review.
5. Optimization/ranking → §9 value function under identical state/data/mandate/cost/uncertainty. Eligible Benchmark is a comparator with no allocation weight; investable passive implementation is an asset subject to constraints. New, Add and Retention comparisons preserve the exact selected Policy definitions.
6. Trading → §7 hurdle + §11 state transitions + §13 independently justified operational threshold; sequential re-optimization and post-rounding checks. Overlay/sensitivity can trigger review or approved input changes and canonical rerun, never arbitrary final-weight edits (§10/12/15).
7. Application/API/UI/batch → shared decision path exposing evidence and missingness, uncertainty/constraint diagnostics, research vs personalized mode and every validation blocker. UI completion alone is not acceptance.

No numeric model performance or financial recommendation is asserted. Provider availability/licensing, PIT timestamps, histories, capital scale/capacity and tax feasibility require separate evidence before data implementation is frozen.

## Design decisions still required
After mandate: select universe/provider evidence contract and durable schema; define forecast/event/wealth semantics and baseline; calibrate U_objective and U_risk separately on development/validation data; define stress binding status and horizon-specific joint budgets; define numerical tolerance, ruin handling, solver and stability acceptance; define exact comparison experiments and actionable state transitions. Unknown residual margin or cost is not silently zero. Optional fractional sizing needs independent calibration; it is not a default multiplier.

## Delivery phases and acceptance
| Phase | Deliverable | Required review and exit evidence |
|---|---|---|
| 0 | Governance bootstrap and offline consistency checker | Sol pre-review → scoped ADR freeze → Terra implementation → isolated tests → Sol post-review; no model acceptance |
| 1 | Mandate/risk research editor, policy statuses, security master and PIT storage/API/batch | Astra/Sol review before semantics freeze; DB migration roundtrip in dedicated test DB; actual writer/API/UI lineage and missingness/approval rejection evidence |
| 2 | Forecast bridges, paths, ledger, wealth/risk/optimizer, distinct rankings/actions | Independent formula/numerical review, adversarial accounting and constraint tests, feasible alternative comparisons, rerun integrity and calibration evidence |
| 3 | Reproducible evaluation and locked OOS | Predeclare data splits, purging/embargo where horizon leakage requires it, sample dependence, metrics/thresholds, trial count, all model/parameter/data/policy versions before final OOS access; frozen baselines and fees |
| 4 | Production-equivalent shadow path | Predefined minimum duration/observations/event coverage, execution/data outage/stability evidence; long-horizon outcome gap remains explicit |
| 5 | Production activation | All material §18 items pass with traceable evidence, independent validation and separate required user approvals |

Phase 3 methodology above is a proposal awaiting review and data feasibility; no dates, thresholds, confidence levels or sufficient observation counts are guessed. Development/validation data can calibrate; final OOS changes invalidate that OOS. Simulated and overlapping long-horizon outcomes cannot substitute for independent realized evidence.
